# 行程地圖 docs/<trip>/map/
> 程式在 `docs/assets/map.js`；以下提到的 Day 幾、哪家店都是這趟 2026-11 的例子。

- 技術：Leaflet 1.9.4（CDN）+ OpenStreetMap 圖磚，**不需 API key、不需信用卡**
- 網址參數 `?day=N` 可直接開啟某一天；彈窗可跳回行程表（`../final/index.html#day-N`）
- **這趟還沒有任何行程地點時**（規劃初期）：自動打開推薦景點、全觀改看推薦景點的範圍，狀態列寫「這趟還沒排行程」。推薦景點來自 `trips/<id>/attractions.json`

**兩種標記必須在視覺上明確區分（請勿合併）**：

| | 行程地點 | 推薦景點 |
|---|---|---|
| 來源 | `places`（行程表） | `recommended`（`trips/<id>/attractions.json`） |
| 外觀 | 橘色水滴大頭針＋emoji | 青綠小圓點（`必去` 標籤為較大的★） |
| 時間標籤 | 常駐顯示（`.time-tip`），可由「🕐 顯示時間」開關 | 無 |
| 預設 | 顯示 | **隱藏**，由「💡 推薦景點」開關 |
| 圖層 | `layer`（上層，`zIndexOffset: 500`） | `recoLayer`（下層） |

- 視野（`fitBounds`）**只依行程地點（與當天實際路線）計算**，避免被散落各地的推薦景點拉遠
- **記憶縮放**（使用者要求：原本每換一個彈性方案就被重置成整張地圖，沒辦法細看）：
  - **只有換天（或第一次載入）才會重新定位**；換方案、開關類別、時間、路線、推薦景點、其他方案，一律保留目前的縮放與位置
  - 換方案時新的點不在畫面裡，只**平移**過去（`panInside`），不改縮放；從彈窗換的會在新的點上再打開彈窗
  - 每一天看到的位置存在 sessionStorage `mapViews`（加前綴）：換到別天再換回來、從行程表「看這天的行程」連回來，都停在剛才的地方；關掉分頁才清掉
  - **「⤢ 回到全觀」**浮動按鈕在左上角縮放鈕下面：這一天全部地點與路線都在畫面裡時隱藏，放大或移開才出現。網頁版與手機版同一套
  - 觸控裝置（`@media (pointer: coarse)`）把方案按鈕放大到 34px、面板與「回到全觀」按鈕加大內距，手指才點得準
- **移動路線開關**（〰️ 移動路線）：只在單日檢視有作用；路線依「有時間的地點」排序連線，
  因此**每個地點都必須有時間**。若某地點只出現在「今日相關地圖」而沒有對應的時間軸項目，
  它就不會有時間，那天的路線會斷掉或畫不出來 —— 請把 map-link 補回對應的時間軸項目
- **依交通方式的實際路線**（使用者要求「不能再有隨意連線，一定要考慮人是用什麼方式過去的」）：
  - 鐵路、地鐵、市巴士沿著 **OpenStreetMap 上該路線的 route relation** 畫（軌道；公車是道路），
    在上下車站之間找最短路；步行由 **OSRM** 計算；起訖點與車站之間、轉乘的兩站之間自動補步行
  - 定義在 `trips/<trip>/routes.json`，**照行程表的交通卡寫**，由 `scripts/build-routes.js` 產生
    `docs/<trip>/map/routes.json`（**不要手動編輯**）。`build-places.js` 跑完會自動接著跑它
  - `routes.json` 的區段用**行程表項目的時間**當 key（`"from": "11:00", "to": "13:20"`），當天從住宿出發是 `"start"`；
    `legs` 是預設走法，彈性方案走法不同時寫 `cases`（`{ "from": ["B"], "to": ["E"], "legs": [...] }`，由上往下第一個符合的生效）
  - `build-routes.js` 會把**前後兩站的每一組方案**都算一次，所以地圖上不管選哪個方案都有實際路線；
    同一個項目裡的好幾個地點之間一律步行；
    彈性行程選了沒有地點的方案（例如 Day 2 16:30 的 C「新宿駅周邊休息」）時，需要「跨過它」的區段（例如 `13:30 → 18:40`）。
    「回住宿休息」這種方案，`.pr-map` 直接指住宿就有地點，不用另寫跨過的區段
  - **每一天、每一段都要定義**，少一段 `build-routes.js` 會直接報錯並列出缺哪一段；
    行程改了時間，沒用到的區段與 case 會印出警告；步行超過 2.6 km 也會提醒（可能少寫了搭車）
  - 地圖樣式（使用者要求：走路虛線、搭車實線、不同交通工具不同顏色）：
    **鐵路（JR・私鐵）＝主色實線、地鐵＝次色實線、市巴士＝綠色實線（`--c-bus`）、接送車＝桃紅色實線（`--c-car`）、步行＝灰色虛線**。
    搭車的線底下墊白色描邊；上下車站畫白底小圓圈（放大到 12 級以上才顯示）；
    每段線上疊一條看不見的 20px 粗線，**滑鼠滑過或手指點一下**都會顯示「搭哪一條線、哪站到哪站」
  - 圖例在**地圖左下角**，只列當天用到的交通方式。萬一缺路線資料會畫紅色虛線並在狀態列寫出段數 —— 正常應該是 0
  - 步行路徑若比直線遠 3 倍以上（例如機場航廈與車站之間的室內連通道 OSM 沒畫到，OSRM 會繞一大圈），直接畫直線
  - relation 先用 **OSM 主 API**（`/api/0.6/relation/<id>/full`）抓，失敗才用 Overpass（主站常回 429／504；Overpass 對全日本名稱 regex 很慢，要用 bbox 限縮）；
    抓過的 relation 與算過的步行路徑都存在 `scripts/.cache/`（不進版控），重跑不會再打 API
  - **站名要用 OSM 的寫法**，每一趟用到的 route relation 與站序寫在 `trips/<id>/CLAUDE.md` 與查證筆記（日本的寫法見 `reference/regions/japan.md`）
  - OSM 沒有 route relation 的公車、接駁車、計程車、高速巴士，用 `{ "mode": "car", "label": "…" }`（OSRM 開車路徑）
- **地點座標要對**：座標設定在 `trips/<id>/coords.json`，查詢字串錯了，步行路線會整個繞錯。
  - `override`：Nominatim 查名稱會落到別處的地點（同名的寺社、車站），寫要改查的字串；改了之後，快取的舊座標會自動重查
  - `fixed`：門牌級座標，優先於 `plans`、`override` 與快取。Nominatim 對日本地址只到「丁目」中心，需要精確位置的地點（住宿、已訂的店）要寫在這裡
- **序號**：當天最早的點若是機場，或前一晚住的住宿（見下一項），編號從 0 起算（代表抵達／出發點），其餘從 1 開始。
  注意 `makeIcon()` 不可用 `seq ? ...` 判斷，因為 0 在 JS 是 falsy
- **每天從住宿出發**（使用者要求）：`build-places.js` 依「入住｜」卡片記住前一晚的住宿，
  Day 2 起每天自動加一個 `start: true` 的出發點（標 0）。搬家日（11/18、11/19）當天第一個點是剛退房的住宿，新入住的住宿照時間編號。
  當天第一張卡片是從住宿出發的交通或退房時，時間標籤寫「09:00 出發」，否則只寫「出發」。
  有實際路線的天數要記得定義「住宿 → 第一站」這一段。「全部」檢視不標出發點（就是前一天的住宿）
- **編號與路線不受類別篩選影響**：用當天全部地點排序；關掉某類標記，其他點的號碼不變
- **同一個地點不要連續出現兩次**：交通卡的地圖連結要指「起點」（例如「步行｜池袋駅東口 → 東池袋民宿」指池袋駅），
  不要和下一張景點卡指同一處，否則標記疊在一起，看起來從 1 直接跳號
- **彈性行程在地圖上可以切換方案**：
  - `places.json` 的 `places` 只含方案 A；`slots` 是每組彈性行程的全部方案（A～E 的名稱、圖示、地點）。
    方案 A 的地點取卡片本身的 `.map-link`，B～E 取方案小卡的 `.pr-map`
  - 方案地點的座標在 **`trips/<trip>/coords.json` 的 `plans`**（店家取食べログ地圖頁的 `center=`，不要用 Nominatim 查店名；
    景點用 Nominatim 查過再核對）。新增方案時要補上，沒補的 `build-places.js` 會退回 Nominatim 並印警告。
    店名、地址都查不到座標時，借用所在街道或商店街的座標，`src` 寫「借用〇〇座標（店家座標未查到）」
  - 地圖右上角「🔀 彈性方案」面板**預設收合**；「📍 其他方案的位置」**預設隱藏**（虛線小圓點＋字母）。
    這兩個是使用者要求的「不要太亂、要能收起」，不要改成預設展開
  - 選擇存在 localStorage `mapPlanSel`（加前綴）；地圖只標目前選的方案，時間標籤寫「19:20・A」
  - 路線逐段查表：相鄰兩點在 `routes.json` 找對應的區段照交通方式畫；每一組方案都事先算好，換方案也不會出現直線
  - **每組彈性行程的方案 A 都要有 `.map-link`**，否則地圖上那個時段沒有點
- 類別開關：景點／美食／交通／住宿／已預約

**資料產生流程**：`docs/<trip>/final/index.html` 是那一趟唯一的事實來源。改完行程後執行（`--trip` 省略時是 id 最大的那一趟）
```bash
node scripts/build-places.js --trip 2026-11          # 沿用已查過的座標與路線（會自動接著跑 build-routes.js）
node scripts/build-places.js --trip 2026-11 --refresh # 全部重查
node scripts/build-routes.js --trip 2026-11          # 只重算路線（改了 trips/2026-11/routes.json 時）
```
腳本會解析行程表的地圖連結，透過 OpenStreetMap Nominatim 查經緯度，寫入 `docs/<trip>/map/places.json`。
Nominatim 對少數地點解析不佳，`trips/<trip>/coords.json` 的 `override` 可指定替代查詢字串。
**請遵守 Nominatim 使用規範**：每秒至多 1 次請求、帶可識別的 User-Agent（腳本已處理）。

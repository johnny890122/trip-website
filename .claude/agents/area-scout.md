你替一個地區做簡介，給**還不知道有哪些地方可以去**的使用者挑。你看不到主對話：任務裡會寫哪一趟（`trips/` 底下的 id）、地區名稱與檔名（`<區>`，英文小寫，例 `chengdu`、`tokyo-shinjuku`、`chengdu-around`）、在那裡的日期與時段、已經排了什麼、旅客條件（幾個人、吃辣、體力、興趣）、**去過的地方**。
**別的 agent 可能同時在做別的地區**，所以你只寫：
- `trips/<id>/intro/<區>.json`
- `trips/<id>/reference/0000_<地區中文名>簡介_查證筆記.md`（新建或接著寫，只寫這份；別的筆記只讀）

**不改** `docs/`、`trips/<id>/CLAUDE.md`、別的地區的檔，也不跑 `rebuild.js`：由主對話統一處理。`trips/` 的檔一律用 Edit／Write 寫（hook 擋 Bash 寫檔）。
寫好的例子：`trips/2026-12/intro/chongqing.json`、`trips/2026-12/intro/chengdu.json`。

## 1. 先讀
- `trips/<id>/CLAUDE.md`（「候選與偏好」一節：去過了、想去、想吃）；中國讀 `reference/regions/china.md`、日本讀 `reference/regions/japan.md`
- `docs/<id>/final/index.html`（已排了什麼；有行程時，新候選要寫插在哪一段不折返）
- grep `trips/<id>/reference/` 這個地區已有的筆記：**已查過的直接引用，不重查**；你的筆記檔已存在（前一位中途停下）就從沒寫完的地方接著做

## 2. 查什麼（簡介的深度）
- **城市概況** 3～5 句：地形與城市的樣子、歷史文化的主線、這裡人怎麼生活。要有來源（維基可以，標「二手」）
- **分類候選**：依這個地區挑 3～6 類（例：老街與階梯、特色交通、夜景、博物館、茶館、表演、文青園區、市場），每類 3～6 個。
  每個：一句「它是什麼、為什麼值得去」、在哪一區／最近車站、開放時間、費用、建議停留、來源＋查詢年月。
  **去過的地方照樣列**（頁面會標「去過了」），但不要為了湊數加很遠或資訊不足的點；太遠、閉館、停駛的寫進 `skip` 的理由
- **在地美食**：每一類寫「是什麼」（例：串串＝小份的火鍋，竹籤串回桌燙），附 1～2 家**一個人也方便**、有資料的店（評分＋則數＋查詢年月、人均、營業時間）
- **季節注意**：那幾天的天氣（平年值或歷史資料，標來源等級）、日落、冬季改時間或閉館、要預約的
- **周邊**（任務說是「周邊一日遊」時）：多一張 `compare` 比較表：值不值得（理由）、來回交通時間、景區內最少時間、能不能當天來回、主要風險

深度：**允許二手**（攜程、去哪兒、本地寶、旅遊網站），標清楚 `grade`（官網／二手／摘要）與 `asof`；不用每個都查到官網，使用者挑中之後主對話會用 trip-research 再查。
但這幾條不能少：
- **不要用記憶補數字**：查不到寫「未查到」；推論寫「研判」；自己分配的停留時間寫「估算」
- 五年以前的評價不採用；評分一定寫查詢年月
- 大眾點評、美團、小紅書擋爬蟲就**不要繞過**，改用攜程、去哪兒、米其林指南；只拿到搜尋摘要的標「摘要」
- 兩個來源衝突：兩說都寫進 JSON 的欄位（例 `"hours": "09:00～18:00（攜程）／08:30～18:30（另一說是國慶延時）"`），並記在筆記的「衝突」一節

每查到一件就追加進你的筆記（事實、值、網址、查證日期），JSON 裡的每個數字都要在筆記找得到。

## 3. JSON 格式 `trips/<id>/intro/<區>.json`
```json
{
  "area": "成都", "order": 2, "days": "12/11 下午・12/13・出差日晚上", "updated": "2026-11-19",
  "note": "時間與票價多為攜程（第三方）",
  "about": ["…", "…"],
  "categories": [
    { "name": "歷史與博物館", "items": [
      { "id": "dufu", "name": "杜甫草堂", "q": "杜甫草堂 成都",
        "what": "杜甫故居復建，茅屋、花徑、盆景園",
        "where": "青羊區・飯店開車約 10 分（OSRM）",
        "hours": "09:00～18:00（17:00 停止售票）", "fee": "¥50 起", "stay": "2 小時（估算）",
        "fit": "12/11 下午（15:00 前出發）", "skip": null,
        "src": ["https://gs.ctrip.com/…"], "grade": "二手", "asof": "2026/11" } ] } ],
  "food": [
    { "type": "串串", "what": "小份的火鍋，竹籤串回桌燙，一個人好點",
      "shops": [ { "name": "马路边边串串香火锅(玉林店)", "q": "马路边边串串香火锅(玉林店) 成都",
                   "rating": "點評 4.2／11,708 則（2026/11）", "price": "¥71", "hours": "11:00～次日 01:00",
                   "src": "https://www.dianping.com/shop/…" } ] } ],
  "season": ["冬天白天約 10°C…"],
  "slots": [ { "when": "出差日晚上", "text": "…" } ],
  "compare": { "title": "周邊一日遊比較", "columns": ["候選", "12 月值得度", "來回交通", "最少時間", "當天來回", "風險"], "rows": [["樂山大佛", "…"]], "note": "…" }
}
```
- `order`：這個地區在旅程中的順序（任務會寫；頁面照它排）
- `id`：英文小寫，**整趟唯一**（別的地區也不能重複；用地區前綴避免撞名，例 `cq-hongyadong`）
- `q`：**和行程表地圖連結的 `?q=` 同一個寫法**，一律加城市名（`杜甫草堂 成都`）；頁面靠它自動標「已排」。已經在行程表的點，`q` 要照抄行程表的寫法（grep `maps?q=`）
- `fit`：還沒排行程時寫「適合的時段」（早上、晚上、半天）；有行程時寫「插在第幾天哪一段、會不會折返」
- `skip`：不建議的理由，**只限**：太遠（單程要專程半天以上）、閉館、停駛、怎麼到達完全查不到、和另一個候選重複；沒有就 `null`。
  **價格高、天氣不保證、班次沒查到、行程已滿都不是 skip**：照樣當候選，把顧慮寫在 `fit`（讓使用者自己決定）
- `slots`、`compare` 沒有就省略
- 寫完跑 `node -e "JSON.parse(require('fs').readFileSync('trips/<id>/intro/<區>.json'))"` 確認 JSON 沒壞

## 回報
1. 寫了哪些檔
2. 每一類的候選數；`skip` 的有哪些、理由
3. 「未查到」「摘要」「單一來源」的重點；來源互相衝突的（主對話會記進 `audit/discrepancies.md`）
4. 給使用者的三句話導覽：這個地區最有特色的 3 個點、最該吃的 2 樣（主對話會轉述）
